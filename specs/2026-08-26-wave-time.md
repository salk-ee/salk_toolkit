# Auto wave_time survey-date column

**Modules:** `salk_toolkit/validation.py`, `salk_toolkit/io/pipeline.py`, `salk_toolkit/io/sources.py`; SIP `default_settings.py` (companion PR).

## Goal

Multi-wave datasets need a categorical time field for modeling and plotting, and until now it
was hand-maintained per project (Estonia's `t_cat` + `stk.rel_wave_times`, ad-hoc `"wave":`
FileDesc keys). Each wave's meta now declares when it was collected, and every load derives an
ordered categorical `wave_time` column from those dates automatically — including when waves
are combined, at any nesting depth.

## Design

**Meta declares the date.** `DataMeta` gains `collection_center` alongside the existing
`collection_start`/`collection_end`. A meta's survey date resolves to `collection_center`,
else the start/end midpoint. Convention (see the `stk-data-annotations` skill): fill all
three; `collection_center` is the *mean of per-row collection dates* (center of mass), since
fielding is usually front-loaded and the midpoint sits late.

**Injection is a pipeline stage.** `_inject_wave_time` runs in `process()` right after
`_inject_files_block`, following the same pattern: a `generated` block named `waves` holding
one ordered categorical column `wave_time`, categories = ISO date labels sorted
chronologically. Per source frame: a frame already carrying the column (a nested annotated
child) keeps its per-row values; a frame without one gets this meta's date as a constant; a
frame with neither, in a load where others have dates, gets NA plus a warning. A load with no
dates anywhere is silently unchanged — the feature is invisible until metas are dated.

**Combining stays chronological.** Multi-file loads reconcile categories via
`_fix_meta_categories`, which appends novel categories in first-seen order.
`_sort_wave_time_block` re-sorts the waves block by `pd.to_datetime`, recasts frame dtypes to
the ordered sorted categorical, and sets `hidden = single wave` (so a lone wave doesn't show
as a constant dashboard filter, but combined waves do). It runs both inside injection and
after the `_load_data_files` category fix — the latter covers `read_and_process_data`
combining already-processed sources without a parent meta, where the block arrives via the
last file's meta.

**Nesting composes.** Each child meta injects its own constant on load; a parent (meta or
`DataDescription`) sees children's columns and only unions + sorts. Dates on the children
alone are sufficient; a parent's own dates apply only to files lacking both column and date.
Labels being ISO dates means metric time is recoverable anywhere via `pd.to_datetime` on the
category names — there is deliberately no separate numeric mapping to drift out of sync.

**Knob.** `DataMeta.time_field`: `false` disables, a string renames (default `"wave_time"`).
A hand-declared column of the same name anywhere in the structure suppresses injection.

**SIP side** (companion change): `wave_time` joins the calibrated `priors.scale` (0.5, same
as the old `t` convention) and `gp_nugget` (0.1) tables, and `run_stack` auto-appends it to
`population.randomize` when used as a model input but absent from the population.

## Implementation notes

- The `waves` block deliberately does not reuse the `files` block: `files` is hidden whenever
  a single file is loaded, but `wave_time`'s visibility must depend on the number of *waves*
  after combining, which only `_sort_wave_time_block` can decide.
- Overwriting an all-NA inherited column with the outer meta's date is intentional: a dateless
  child under a dated parent adopts the parent's date.
- In the `read_and_process_data` multi-meta path the combined meta is the *last* file's
  ("last file is the basis"): if only the last meta is dateless, the column still lands in the
  concatenated frame but the meta carries no `waves` block, so meta-driven consumers (pp,
  dashboards, SIP) won't see it — dating the last wave's meta is what makes the field flow
  through, consistent with the existing block-alignment rule.
